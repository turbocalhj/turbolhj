P1-1 / P1-2首屏 4MB

两件事分开做：视频先降规格，字体按字符分片。字体分片不需要改设计，只改 @font-face 的 unicode-range，浏览器只下载页面真正用到的片。

# 视频：1080p → 720p，CRF 30 左右
ffmpeg -i hero.mp4 -vf scale=-2:720 -c:v libx264 -crf 30 -preset slow -an hero-720.mp4

# 字体：按常用字/次常用字切两片
pyftsubset NotoSansSC-subset.woff2 --unicodes=U+4E00-9FA5 \
  --flavor=woff2 --output-file=noto-sc-a.woff2

预期：首页首屏从 4.07MB 降到 1MB 以内；字体片只在正文页加载，说明页几乎不付成本。

03分维度小结

性能

本机实测 CLS 0.0005、FCP 540ms、DCL 479ms，说明渲染本身很干净，短板全在字节数：视频、字体、岛屿、搜索索引四项加起来约 5.2MB。优先做 P1-1 到 P1-4，收益最大。

SEO

站点结构（sitemap、canonical、RSS、双链）已经比多数个人站完整。真正的问题只有 P0-1 一条，其余是 P2-7/P2-8 这类锦上添花：结构化数据、分享图、lastmod。

可访问性

键盘可达性基础扎实（skip link、焦点样式、entry 封面的焦点陷阱），缺口集中在 P2-1 对比度、P2-2 触控尺寸、P2-3 搜索面板焦点循环，都属于小改动。

服务端与维护

零依赖实现很克制，密码哈希与签名会话写得规范。风险点是 P3-5「首个注册即管理员」与 P3-4 全域 CORS，若服务未来要放到公网，这两项必须先处理。

04建议的动手顺序

  1. 先修 P0（半天）：标题一行、两处窄屏断点、表格容器。都是低风险改动，改完用 320 / 375 / 1440 三个宽度回归一遍。
  2. 再压首屏（一天）：视频降规格、字体分片、岛屿拆包。改完用 Chrome DevTools 的网络面板复核首页传输是否低于 1MB。
  3. 然后收可访问性（半天）：对比度、触控尺寸、搜索焦点循环、主题按钮语义。
  4. 最后做 SEO 与服务端加固：404 页、Article 结构化数据、注册开关、CORS 收敛、CSP。
  5. 可选的长期项：搜索索引拆分与中文分词、长笔记分页、动效层合并。

05体检口径

  • 基线数据来自 npm run build 与 npm run check 的实际输出；页面体积与 DOM 规模来自 serve.js 本地服务的真实响应。
  • 窄屏与焦点行为使用本机 Chrome（headless，Playwright 驱动）在 320 / 375 / 1440px 三个视口实测，非推断。
  • 对比度按 WCAG 2.x 相对亮度公式计算；触控尺寸取渲染后的实际盒子尺寸。
  • 本轮只做诊断，没有修改站点任何文件；dist/ 是重新构建的产物，与源码一致。
